# Eduri Guest Rooms Architecture

Status: public guest-room foundation implemented; production acceptance in
progress.

Date: 2026-08-09.

## Product model

A room is the shareable collaboration boundary. A room may contain Board,
Code, Call, or any combination of them. A guest room has at most one resource
of each kind. Account-owned rooms use the same room identity and resource
contracts, but may later contain multiple ordered resources.

The public routes are:

- `/` - Board, Code, Call, and account entry points;
- `/board` - a local-first solo Board;
- `/code` - a local-first solo Code workspace;
- `/room/:shareId` - the first available resource in a room;
- `/room/:shareId/board`, `/code`, and `/call` - independently addressable
  room resources.

Creating a room from a solo tool must promote the current resource, including
its current durable state, rather than create an unrelated empty resource.
Creating a Board or Code resource from Call follows the same rule in reverse.
Solo promotion creates an initialization draft whose token is sent only in
same-origin JSON request bodies. The room becomes active only after every CRDT
update and immutable asset/blob is durable and the client finalizes the draft.
Failure or cancellation before finalize cancels the server draft before local
guest caches are cleared, so a retry cannot leave an empty shareable room.
Immediately before the first finalize request, the browser persists the draft
capability as bounded same-origin recovery metadata. Once that request has
been sent, a network failure is ambiguous: the client does not cancel the
draft or clear its guest caches. The next promotion attempt retries the
idempotent finalize for that same room before it can create another draft.
Recovery records are scoped to the individual draft, so concurrent tabs cannot
overwrite or clear each other's attempt. A successful response is cleared only
after local guest resources close and a final cancellation check passes. A
definitive invalid, missing, or expired draft response (`400`, `404`, or `410`)
clears only that exact attempt and continues through any other pending attempt
before creating a fresh draft; a network failure or `5xx` response preserves
the attempt.

## Identity and access

`shareId` is a 256-bit base64url capability generated by the server. It is
never sequential, appears only in the URL path, and is not written to access
logs by application code. Possession grants guest read/edit access to the
guest room. Resource IDs are stable UUIDs but are not access credentials.

The guest-room call shell and every custom LiveKit surface follow the global
document theme. Switching presentation theme only changes inherited palette
tokens; it must not reconnect, remount, or otherwise disturb the media room.

The initial HTTP foundation stores rooms and resources independently from
authenticated lessons. `owner_user_id` is nullable so an authenticated user
can create through the same API without changing room identity later. Guest
Board/Code sync tickets must contain a server-authenticated ephemeral guest
principal derived from the room capability; awareness may not trust a client
supplied identity or display role.

All public mutations are same-origin-only, bounded, and rate-limited. A generic
"activity" endpoint is forbidden: only a successfully committed Board update,
Code update/file operation/test-case mutation, newly created room resource, or
confirmed Call presence may extend the room lifetime.

## Lifecycle

Guest rooms use a sliding 48-hour inactivity window.

- `GET` metadata, loading a resource, presence-free socket connection, and
  merely viewing content do not count as activity.
- Idempotently requesting an already-present resource does not count.
- Discovering that a Board asset or Code blob is already ready, or replaying a
  completed Board finalize, does not count. Concurrent Board publication
  contenders produce one activity mutation from the committed winner; the
  later CRDT mutation that actually adds or changes a file/object also counts.
- A new room resource counts after its row commits.
- Board and Code ready publication and its activity update commit in the same
  SQLite transaction; expiry or a failed activity update rolls publication back.
- Call activity counts while LiveKit confirms at least one participant, not
  merely when a lobby is viewed or a token is minted. Token provisioning first
  takes a persistent 15-minute activation lease and explicitly creates the
  authorized SFU room; creation of the logical Call resource alone takes no
  media capacity. Repeated token requests do not renew a provisional lease;
  only confirmed presence does. An ambiguous SFU provisioning failure retains
  the bounded lease so a concurrent successful request cannot lose its capacity
  reservation. Polling includes a bounded two-minute late
  confirmation window so a canonical occupied-room result that crosses the
  stored expiry boundary is not discarded. Access, viewing, and token issuance
  still fail at the stored expiry. During the grace window only the physical
  row is retained: an authoritative empty result deletes it immediately, an
  occupied result atomically renews it, and a failed or unavailable poll leaves
  it only until the hard grace boundary. Startup polls LiveKit before cleanup.

On expiry the cleanup transaction hashes the share capability into a bounded
tombstone and deletes the room. Cascades delete resource content, CRDT logs,
files, test cases, logical assets, pending uploads, and runner state. The same
transaction deletes guest Board blob metadata and places every published and
staging storage key in a durable garbage queue. Physical unlink runs after
commit, treats missing files as success, checks that a key has not become live
again, and leaves failures queued for retry after maintenance or process
restart. The raw share capability and room content are not retained. A
tombstone exists for 30 days solely to return HTTP `410 ROOM_EXPIRED`;
afterward the same URL returns 404. The expired client view contains
`Сеанс завершён` and one Home action.

LiveKit media rooms are ephemeral execution state. Global `auto_create` is
disabled. The application explicitly creates a two-person room only after
lesson or guest capability authorization, and join JWTs have no room-create
grant. Management RPCs use an explicit private loopback/RFC1918 origin; the
public `/twirp/` path is closed. `empty_timeout` closes the media process when nobody remains.
A current activation generation has a stable LiveKit room name. When an
authoritatively confirmed-empty provisional lease expires, one transaction
queues deletion of that old opaque room name, advances the Call room generation,
and releases the capacity slot. A later activation therefore uses a distinct
name and cannot race a delayed deletion of the abandoned room, while the logical
Call resource and its public URL stay stable. Room expiry/cancellation queues
the current media-room deletion before cascading guest content, so cleanup is
not lost across a management outage or process restart.

## Storage

Migration 8 introduces:

- `guest_rooms`: capability and inactivity metadata;
- `guest_room_resources`: stable typed resources, currently unique on
  `(room_id, kind, ordinal)`;
- `guest_room_tombstones`: SHA-256 capability hashes with bounded retention.

Migration 15 adds `board_asset_gc_queue` plus transactional delete triggers for
published Board blobs and upload staging files. Guest-room expiry/cancellation
deletes the room-specific `guest-room-<room id>` blob tenant in the same
transaction, so a crash cannot create an untracked private file.

Migration 16 adds Board upload final-path recovery. Board and Code reserve a
staging GC intent before creating `.part` bytes, queue a deterministic final
path before hardlink publication, and synchronously restore that intent if the
publication transaction fails after a concurrent room cascade/GC pass. Active
pre-v16 Board uploads are backfilled with their deterministic final key during
reopen. Slow decode/scan completion rechecks the live room before reading
mutable upload rows and returns `410 ROOM_EXPIRED` after cleanup wins.

Migration 21 adds the monotonic guest Call room generation and a durable
LiveKit delete-room outbox. Its payload contains only the opaque room name plus
retry metadata: never a JWT, API key, guest share capability, user credential,
or participant identity. A generation/CAS acknowledgement cannot erase a newer
enqueue of the same name. The worker runs at startup and independently every
five seconds, drains bounded batches with bounded concurrency, treats `404` as
idempotent success, and retains failures indefinitely with a capped attempt
counter and exponential backoff capped at 15 minutes.

Board and Code content must not be stored as whole-scene last-write-wins JSON.
Their resource tables point to granular CRDT documents and immutable assets.
The room layer owns lifecycle; each resource layer owns validation,
persistence, quotas, compaction, and sync.

## Current status and remaining gates

Implemented:

- public room creation/read/resource-link HTTP foundation;
- 48-hour non-view activity semantics and hashed tombstones;
- rate limits and terminal 410 behavior;
- stable, explicitly provisioned guest LiveKit room/token issuance with
  source-scoped camera, microphone, and screen-share publishing;
- public Home, solo Board, solo Python, and guest Call entry points;
- guest Code state-vector sync with a durable local update log/outbox,
  idempotent ACK replay, multipart cold sync, and authenticated awareness;
- capability-scoped immutable Code blob upload/download with local verified
  caching, bounded fail-closed ClamAV scanning, and publication before a CRDT
  file reference becomes visible;
- solo Board and Code promotion into a newly created guest resource, with a
  read-only snapshot boundary, durable asset/blob publication, acknowledged
  CRDT transfer, draft finalize before delayed navigation, and server-draft
  cancellation plus partial guest-local cleanup before finalize, together with
  persisted idempotent recovery after an ambiguous finalize response;
- one-hour initialization leases for unlisted promotion drafts, with
  token-hash verification, finalize-once semantics, and cascading cancellation
  or expiry cleanup;
- guest-scoped Board and Code authorization on every HTTP/WebSocket operation,
  allowed-Origin enforcement for every mutation, and terminal revocation of an
  already-connected socket when the room expires;
- durable mutation accounting through `recordResourceMutation`, cascading
  deletion of Board, Code, blob, asset, update-log, and receipt state, durable
  retryable filesystem garbage collection, and bounded hashed tombstones;
- authoritative LiveKit participant polling, lease extension only while at
  least one participant is present, bounded late confirmation across the expiry
  boundary, persistent 15-minute provisional activation slots, generation-safe
  never-occupied room cleanup, and durable restart-safe media-room deletion
  after lease release, cancellation, or expiry;
- two/three-replica convergence, multipart cold sync, duplicate/reordered
  update, offline/reconnect, active-session expiry, SQLite reopen, migration,
  and promotion rollback tests.

Remaining production acceptance work is operational rather than a missing room
protocol: complete the desktop/mobile/touch/stylus browser matrix, run the real
ClamAV EICAR and clean-file smoke tests on the Linux deployment, and exercise a
48-hour lifecycle with production LiveKit polling. The Code workspace's
documented lazy per-file CRDT split also remains a future scaling migration;
the current adapter uses one bounded workspace Y.Doc.
